Analysis: System Errors and Code Improvements for evidence_analyzer.py

Based on the comparison between the extracted JSON (result.txt) and the original PDFs, we identified several recurring errors. Below, we map those errors to specific limitations in the current code and provide actionable recommendations for improvement.

1. Summary of Observed Errors

Error Category	Examples	Affected FIRs
Complainant name	Rajendra → Rajesh; Vijay → Ajun; Samiran → Samadhan; Surname mismatches	0, 83, 84, 85
Accused names	Ashok → Anil; Mashni → Manish; Shamrao → Bhimrao; Surname Hatle → Tile	0, 84, 85
Victim names	Dnyanu → Dattu; Shivaji → Siddhi	84
Property missing / incomplete	Vehicle details not captured in property for theft cases (FIR 83, 86); gold values missing	83, 86, 0

Place / address	Vague "Near residence" instead of full address with landmarks	84, 86
Section mapping	Extra section (IPC 506) not in PDF; missing/incorrect sections	84
These errors indicate that the system often misreads OCR output (especially Devanagari) and fails to reconcile spelling variants, lacks appropriate schema fields, and does not enforce strict parsing of time and place.

2. Root Causes in the Code

2.1. Limited Property Schema (property object)

The current schema only includes cash, gold, documents, and estimated_loss. There is no dedicated field for vehicles, which are a common subject of theft (IPC 379). As a result, the LLM either omits vehicle details or tries to squeeze them into documents or estimated_loss, leading to loss of information.

Code location:

SINGLE_PASS_PROMPT, CHUNK_EXTRACTION_PROMPT, RECONCILIATION_PROMPT all define the same schema.
_normalise_facts() and _empty_facts() also stick to that schema.
2.2. Insufficient Name Denoising in Prompts

Although the prompts include instructions about Devanagari OCR confusions (र ↔ श, etc.) and to cross-reference occurrences, the errors show that the model still picks wrong names, especially when the OCR is poor. The prompt tells the model to pick the most frequent spelling, but it does not instruct it to compare with the structured sections (e.g., the accused list) as the primary source of truth. In many cases, the narrative contains OCR noise, but the accused list in the FIR header is more reliable.

Code location:

SINGLE_PASS_PROMPT – lines containing "CRITICAL: Devanagari OCR name denoising" and "Cross-reference all occurrences".
RECONCILIATION_PROMPT – similar instructions.
2.3. Time Parsing Ambiguity

The prompt says "Always use 24-hour format (HH:MM)" and gives examples, but the LLM still outputs 12‑hour times or misinterprets AM/PM. This may be due to:

OCR misreading numerals (e.g., 14:30 as 02:30 when Devanagari digit ४ is read as २).
The model not consistently applying the conversion rule when the original text uses terms like "दुपारी" (afternoon) or "रात्री" (night).
Code location:

In SINGLE_PASS_PROMPT, under "TIME FORMAT".
2.4. Place / Address Extraction Lacks Completeness

The prompt instructs to extract place, but does not specify that the full address (including landmarks, village, post office, etc.) should be captured. The model often returns a short, vague location.

Code location:

The description of the place field in all prompts.
2.5. Section Extraction Errors

The model sometimes adds sections that are not present (e.g., IPC 506) or misses some. This could stem from:

OCR misreading numbers (e.g., 323 seen as 326).
The LLM over‑generalizing based on the narrative.
Code location:

The sections extraction is driven purely by the LLM; there is no post‑processing to validate against known IPC sections.
2.6. Reconciliation Pass May Not Fully Resolve Conflicts

For long documents, the chunking + reconciliation pipeline uses a separate LLM call to merge partial extractions. However, the reconciliation prompt provides only the full OCR text (truncated to 60k chars) and the partial JSONs. It does not enforce a hierarchy of trust (e.g., favour the header over the narrative). This can lead to inconsistent names if the partial extraction from a narrative chunk contains a wrong variant and the reconciliation does not correct it.

Code location:

RECONCILIATION_PROMPT – it gives equal weight to all chunks.
3. Recommendations for Improvement

3.1. Extend the property Object

Add a vehicles field (array of objects) and an other field to capture any additional property.

New schema proposal:

json
"property": {
  "cash": "string or null",
  "gold": "string or null",
  "documents": "string or null",
  "vehicles": [
    {
      "type": "motorcycle",
      "make_model": "Hero Honda Splendor Plus",
      "registration": "MH15CG3239",
      "value": "45,000"
    }
  ],
  "other": "string or null",
  "estimated_loss": "string or null"
}
Update all prompts and the normalisation function accordingly.

3.2. Strengthen Name Extraction with Priority Rules

In the prompts, add explicit instructions:

“The most reliable source for names is the structured sections (complainant header, accused list) at the beginning of the FIR. The narrative may contain OCR errors. Always use the structured names as the primary source and only fall back to the narrative if the structured section is missing or garbled.”
Include examples of common OCR confusions and how to resolve them.
3.3. Post‑Process Time Output

After receiving the LLM response, apply a simple regex or rule‑based fix to:

Convert any 12‑hour time to 24‑hour (e.g., if it contains "PM" and hour < 12, add 12).
Fix OCR‑induced digit errors (e.g., if the hour is 02 but the minute is 30 and the original text had "दुपारी", infer 14:30). However, automatic inference is risky; a better approach is to enforce the model to output 24‑hour directly with stricter prompt wording and examples.
3.4. Enforce Full Address Extraction

Add to the prompt: “Capture the complete address as given in the FIR, including village, post office, taluka, district, and any landmark. Do not summarise.”

3.5. Validate Sections Against a Known List

Maintain a list of valid IPC sections (and other Acts) and filter the extracted sections to only those that are valid. If a section is not in the list, either discard it or flag for manual review. This would remove false positives like IPC 506 when not present.

3.6. Improve Reconciliation

Provide the most reliable chunk (e.g., the one containing the FIR header) with higher priority during reconciliation.
Instruct the LLM to always trust the header/structured section over the narrative when there is a conflict.
Consider a two‑stage reconciliation: first resolve names, then resolve other fields.
3.7. Add a Consistency Check

After extraction, perform a sanity check:

If sections include IPC 379 (theft), ensure that at least one property item (cash, gold, vehicle, etc.) is present.
If a complainant is also listed as a victim, that is acceptable; but if the complainant is the only victim, that should be the case.
3.8. Improve OCR Preprocessing

For PDFs, if the text layer is missing and we fall back to OCR, consider using a higher DPI (e.g., 300) and performing deskewing to improve accuracy.
For Devanagari OCR, ensure that tesseract-ocr-mar and hin are installed and the language parameter is correctly set (lang="eng+hin+mar"). Also, experiment with --psm 6 (assume a single uniform block of text) to see if it yields better results.
4. Suggested Code Modifications

4.1. Update Schema in Prompts

Modify the JSON schema in all three prompts to include vehicles and other.

4.2. Add Post‑Processing Function

Implement functions like:

python
def normalise_time(time_str: str) -> str:
    # Convert to 24h if needed, handle ranges
    pass

def normalise_sections(sections: list) -> list:
    valid_ipc = set(range(1, 511))  # approximate
    return [s for s in sections if s.startswith("IPC ") and int(s.split()[1]) in valid_ipc]
4.3. Enhance Name Cross‑Validation

Use a fuzzy matching library (e.g., fuzzywuzzy) to detect if two names are likely the same person, and then pick the most complete form.

4.4. Add a Priority Rule in Reconciliation Prompt

Modify the reconciliation prompt to include:

“When you see contradictions between the partial extractions, give highest weight to the chunk that contains the FIR header (complainant details, accused list) and the itemised property section. The narrative may contain OCR errors.”
4.5. Fallback Mechanism

If reconciliation fails (i.e., JSON parse error), do not fall back to the first partial; instead, attempt a second LLM call with a simplified prompt or default to a "manual review required" state.

5. Conclusion

The current system performs reasonably well for straightforward FIRs but suffers from:

Lack of a dedicated field for vehicles in the property schema.
Insufficient handling of OCR‑induced name variations.
Weak enforcement of 24‑hour time conversion.
Incomplete address extraction.
No validation of extracted sections.
By implementing the above recommendations—especially the schema extension and stronger name resolution rules—the accuracy of the extracted data will significantly improve.
